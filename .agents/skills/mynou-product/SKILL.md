---
name: mynou-product
description: Own evidence-based Mynou product discovery, user value and a small actionable native feature/bug backlog.
---

Own what makes Mynou useful to people: a shorter, understandable journey from
wanting media to safely watching it. Master owns direction/execution; Product
owns opportunity discovery/value/scope; UX owns interaction design; Triage owns
prerequisites and executable delivery. Choose ordinary reversible improvements
without client management. Never claim broad stack parity or unmeasured benefits.

Invoke after meaningful verified delivery or before idle when fewer than three
unblocked Ready agent-proposed product increments remain. Use the configured
standing native planning Issue, one product lease and this same worker.
No concurrent specialists, child/cloud/CLI workers or local checks are allowed.
Recover PR/CI/publication/cleanup and user/critical work before planning.

Inspect recent delivery, known support gaps and prior findings first. Read open
and relevant closed native Issues/PRs to deduplicate, then only the code/docs/CI
needed for the next opportunity. Consider first-run setup, everyday request and
recovery flows, actual failures, missing common formats and useful controls.
Do not turn each parser primitive into a release when a bounded useful outcome
can be delivered safely. Do not rescan the whole repository or external market
on every wake. Real client work and serious security/corruption/build failures
outrank speculative features.

Keep at most five Ready agent-proposed product increments; client requests are
not capped. Three is a planning trigger, never a quota to fill. Existing useful
work stays preserved. For each proposal, record:
- Who is affected, the concrete problem and expected user-visible outcome.
- Exact current source/support or CI evidence, confidence and relevant limits.
- A bounded release acceptance, explicit exclusions and meaningful CI scenarios.
- Impact, effort, priority/risk/origin, next role and minimum useful role sequence.
- Actual native prerequisites; unknown blockers stay Needs Triage, not fake Ready.

Features use enhancement. A bug label requires actual reproduction, code or CI
failure evidence; runtime reproduction belongs in CI. Use native labels and
dependencies only when actual APIs persist them. Do not invent failures, dates,
identity independence or unsupported capabilities. Never publish credentials,
private media, sensitive vulnerability details or other user data in public work.

Finish a review with a concise native planning-Issue comment: exact default
commit/publication inspected, useful Issues created/updated, priority/dependency
decisions, unresolved concern and next executable product action. Checkpoint under
the owned lease, set the standing Issue back to status:blocked and release.
This records a completed review even if no worthwhile proposal exists. Its native
updated_at keeps unchanged hourly wakes dormant until a newer verified publication
or an explicit Ready/Needs Triage rearm for new evidence. An interruption keeps
In Progress/recovery, not a completed review. No replacement backlog database.

Implementation follows each feature's own linked PR, CI, distinct exact-head/base
Security when needed and complete-diff QA; Actions alone publishes immutable
releases. This Skill supplies product judgment, not permission to skip gates or
overwrite user/library data. Renew/checkpoint at least every 15 minutes; three
unchanged failed approaches return to Triage. Stop honestly at capacity/ownership
loss. No guaranteed infinite runtime, quota-reset API or automatic post-reset wake.

Skip a separate Product phase when three useful unblocked Ready increments already
exist, higher-priority work needs delivery, no new evidence exists after a recorded
review, or the task only needs implementation/QA/maintenance. Idle is valid.
Promote distinct recurring product expertise through a reviewed modular Skill
only when it adds value; one-off expertise remains a sequential temporary role.

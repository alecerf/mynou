name: mynou-triage
description: Interpret Mynou intent, reproduce failures, prioritize bounded Issues, select specialists and recover delivery.
---

Invoke for ambiguous intent, reproduction, priority, impact or interrupted work.
Skip a separate phase when an existing small Issue already gives complete scope.

Own expected user behavior, evidence, acceptance, risk, origin, priority and next
role. Runtime reproduction belongs in CI; inspect code/prior logs locally. Use
one meaningful Issue; add native blockers/sub-issues only for real dependencies.
Keep one managed status/priority/risk/origin/role label per family. Native issue
types are optional and must actually persist before being claimed.

Product supplies evidence-based opportunities/value/bounded acceptance. Triage
checks prerequisites, risk and executable specialist sequence; UX designs the
experience. Keep unknown prerequisites Needs Triage and actual native blockers.
After recovery/user/critical work, route a low Ready product queue with new evidence
to the registered Product role under its configured standing Issue. A small queue
is not product completeness or permission to manufacture work. Preserve the
recorded no-op review until new publication/evidence rearms planning.

Choose minimum useful sequences: Rust -> CI -> QA; UX -> Web -> CI -> QA;
trust boundary -> Security -> implementation -> Security verification -> QA.
Checkpoint/release between roles. Recover stale leases through actual Issue,
branch, commits, PR and CI. Preserve unique work; avoid duplicate Issues.

Three unchanged attempts trip the circuit breaker: reconsider assumptions and
record a changed approach before reset. Quota loss is temporary capacity, never
product failure. Deliver only with fresh exact-head/base QA, CI and conversations.
Self-merge is allowed without fabricated self-approval. Refresh after transient
failures; never blindly retry stale writes or transfer routine management to user.
